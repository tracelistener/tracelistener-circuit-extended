# Circuit DSP parameter map

How the original Circuit's ARM firmware (build 3592) drives its DSP, which DSP memory each user parameter lands in, and which parts could support new features. It was compiled on 2026-10-10 from the published performance-v2 image. All addresses are in that image; the stock code they describe is unchanged by this project.

**Confidence labels used below**

- **Confirmed**: read directly from code or tables.
- **Inferred**: strongly suggested by parameter counts, ranges and code structure, but not checked against Novation documentation, which this environment could not download.
- **Open**: unknown.

The full list of 299 ARM→DSP accesses is in [`dsp-parameter-accesses.csv`](dsp-parameter-accesses.csv), generated by [`dsp_parameter_map.py`](dsp_parameter_map.py). The DSP code was read with the [dsp56300](https://github.com/dsp56300/dsp56300) disassembler (build steps in [`performance/dsp_lfo_harness/build.sh`](../performance/dsp_lfo_harness/build.sh)).

## Feature candidates

Ranked by usefulness against risk.

|---|---|---|---|---|
| 1 | **On-device delay editing**: time, sync, feedback, width, L/R ratio, slew | Six session parameters (NRPN 1:6–1:11) and a DSP delay block at X:$835–$83B. The firmware already pushes them to the DSP | Low: no DSP change, and the parameters and their storage are stock |
| 2 | **On-device reverb editing**: type, decay, damping | Three session parameters (NRPN 1:18–1:20) | As 1 | Low |
| 3 | **On-device sidechain editing**: source, attack, hold, decay, depth for each synth | Five session parameters per synth (NRPN 2:55–2:59 and 2:65–2:69); DSP X:$2DF–$2E3 and X:$451–$455 | As 1 | Low |
| 4 | **Tempo-synced drum LFO** | The tempo is already in X:$15, and the synth's sync formula is identified ([performance/README.md](../performance/README.md#tempo-sync-findings-not-implemented)) | About 10 more DSP words than the LFO slot holds; needs ARM code moved out of the DSP image | Medium to high |
| 5 | **Synth pan on the device** | Session parameters 36 and 37 (CC 117/118, centred at 64) | Check whether the hardware already exposes them; if not, as 1 | Low |
| 6 | **More modulation sources** | Performance v2 found unused mod-matrix inputs (mod wheel, aftertouch) | Look for other inputs the stock firmware never feeds | Research first |

Candidates 1–3 are the best next step. Each value is a normal stock parameter that the firmware already stores per session, saves, sends to the DSP and accepts over MIDI. The hardware just has no direct control for it. A new control only has to change the parameter through the same path the MIDI receive code uses. Finding that path is the first task.

## How the ARM talks to the DSP

**Confirmed.**

| | Function | Arguments | Notes |
|---|---|---|---|
| Write | `0x0801633C` | r0 = value, with the 24-bit DSP word in bits 31..8; r1 = address | Sends a set-address command only when the address differs from the previous write plus 1, then three data bytes over SPI |
| Read | `0x08016E64` | r0 = address | Returns the word in bits 31..8 |

- **Address format.** Bit 15 selects memory: set = **Y**, clear = **X**. Bits 14..0 are the word address, and writes auto-increment. So `0x8105` means Y:$105 and `0x1E65` means X:$1E65. Read requests set bit 23 of the command word.
- **DSP side.** The host-command interrupt at P:$0167–$0191 decodes these commands.
- **Program load.** The DSP program (10,253 words, loaded at P:$0000) is stored in ARM flash at `0x08025B74`, with a 6-byte header at `0x08025B6E`. Unused interrupt vectors inside it hold this project's DSP LFO (P:$01–$23) and ARM helper code (P:$24–$3D, P:$70–$B3, P:$DC–$FF).

## Stock parameter tables

**Confirmed.** These are the CC tables mapped by the [CC-remap work](../cc-remap/). Each part has one 8-byte record per parameter, and the record index is the parameter number the getters use:

| Part | Group | Records | Table |
|---|---|---|---|
| Synth (×2) | 0x00 / 0x01 | 310 | `0x0802DBC0` |
| Drums | 0x10 | 28 = 4 drums × 7 | `0x0802E810` |
| Session | 0x20 | 38 | `0x0802D9CC` |

**Record layout.**

| Byte | Meaning |
|---|---|
| 0 | Internal parameter id (not always equal to the record index) |
| 2–3 | Flags (0x40C0 marks a centred, bipolar parameter) |
| 5 | Maximum value |
| 6 | 0xFF = CC; 1 or 2 = NRPN high byte |
| 7 | CC number, or NRPN low byte |

The getters `0x0800D8E4` and `0x08025594` take r0 = group and r1 = parameter number.

## Synths

**Confirmed layout, names open.** Synth 1's DSP parameters span about X:$185–$2EB, indexed by voice or oscillator in many places. Synth 2's copy sits $172 higher (for example, the controller targets are X:$2D7 and X:$449, as found by performance v2). The sidechain blocks above follow the same stride. The 310 synth records cover every patch parameter, and [`cc-remap/circuit_cc_remap_patch.py`](../cc-remap/circuit_cc_remap_patch.py) names the CC-mapped ones. Mapping each record to its DSP word is the next research step if a synth feature is wanted.

## Open questions

- **What sets X:$40?** Possibly the DSP's start-up code, or an auto-incrementing write sequence. This matters for exact tempo-sync timing.
- **84 unresolved writes.** 59 compute their address and 25 set it before a call (see the CSV). Most are in voice and patch loading, `0x08016400`–`0x08016E60` and `0x08019290`–`0x080195F0`.
- **Session parameter 21** (NRPN 1:21, on/off).
- **Reverb type and decay** have no fixed-address DSP write; find where they land.
